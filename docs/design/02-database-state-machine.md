## 1. Schema đầy đủ

### Quy ước thiết kế

| Quy ước | Lý do |
|---------|-------|
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` làm PK | Cho phép seed id cố định trong demo data |
| `TIMESTAMPTZ` cho mọi timestamp | Lưu timezone, API đổi sang epoch ms cho frontend |
| `VARCHAR + CHECK` thay vì PostgreSQL ENUM | Thêm giá trị mới không cần `ALTER TYPE`; map thẳng với `@Enumerated(EnumType.STRING)` |
| SHA-256 của Bearer token trong bảng `sessions` | Lộ DB không dùng lại được token |
| Soft delete bằng `deleted_at` trên `problems` | Bài nộp cũ vẫn tham chiếu được problem đã "xóa" |

### Bảng hệ thống

| Bảng | Cột chính | Constraints quan trọng | V |
|------|-----------|----------------------|---|
| `users` | id, username (MSSV), full_name, role, password_hash | ck: ADMIN phải có password_hash; STUDENT username ~ regex `^[A-Z][0-9]{2}[A-Z]{4}[0-9]{3}$`; UNIQUE(upper(username)) | 1 |
| `sessions` | token_hash (BYTEA 32B), user_id, expires_at, revoked_at | idx expires_at WHERE revoked_at IS NULL | 1 |
| `problems` | id, title, difficulty, tags (TEXT[]), statement, time_limit_ms, checker, deleted_at | GIN index trên tags[]; soft delete; `trg_problems_updated_at` | 1 |
| `test_cases` | id, problem_id, position, input, expected_output, is_sample | UNIQUE(problem_id, position) DEFERRABLE — cho phép reorder trong 1 transaction | 1 |
| `contests` | id, title, start_at, end_at, penalty_minutes | ck: end_at > start_at | 1 |
| `contest_problems` | contest_id + problem_id (PK), label | UNIQUE(contest_id, label) DEFERRABLE | 1 |
| `contest_participants` | contest_id + user_id (PK), registered_at | — | 1 |
| `workers` | id (VARCHAR), status, register_payload (JSONB) | status IN ('IDLE','BUSY','DEAD') | 1 |
| `submissions` | id, user_id, problem_id, contest_id, source_code, status, verdict, score, attempts, **attempt_token** | Xem bảng chi tiết dưới | 1 + V11 |
| `submission_test_results` | submission_id + test_index (PK), status, time_ms, memory_kb, output_preview | status IN ('AC','WA','TLE','MLE','RTE','SKIPPED') | 1 |
| `submission_events` | id, submission_id, event, worker_id, attempt, note | event IN (IN_QUEUE, ASSIGNED, COMPILING, TESTING, SCAN, REJECTED, REQUEUED, FINISHED, FAILED, REJUDGE) | 1 |
| `system_logs` | id, level, message, worker_id, submission_id | ix_system_logs_created DESC | 1 |
| `contest_violations` | contest_id, user_id, violation_type, count | Proctoring | 3 |
| `plagiarism_reports` / `plagiarism_matches` | Kết quả Winnowing fingerprint | Gắn contest_id, problem_id | 5 |
| `classrooms` | id, name, semester, created_by | LMS — 1 classroom → many students & contests | 7 |
| `courses` / `course_units` | id, title, is_published; unit: course_id FK cascade, order_index | UNIQUE(course_id, order_index); CASCADE DELETE | 8 |

### Chi tiết bảng `submissions`

```sql
CREATE TABLE submissions (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY (START WITH 1001) PRIMARY KEY,
    user_id           BIGINT      NOT NULL REFERENCES users(id),
    problem_id        BIGINT      NOT NULL REFERENCES problems(id),
    contest_id        BIGINT,                             -- NULL = luyện tập
    language          VARCHAR(16) NOT NULL DEFAULT 'cpp17',
    source_code       TEXT        NOT NULL CHECK (octet_length(source_code) <= 65536),

    -- Giới hạn chụp lại lúc nộp (admin sửa đề sau không làm sai kết quả cũ)
    time_limit_ms     INTEGER     NOT NULL,
    memory_limit_mb   INTEGER     NOT NULL,

    status            VARCHAR(12) NOT NULL DEFAULT 'IN_QUEUE'
                      CHECK (status IN ('IN_QUEUE','COMPILING','TESTING','FINISHED','FAILED')),
    verdict           VARCHAR(3)  CHECK (verdict IN ('AC','WA','TLE','MLE','RTE','CE','SEC')),
    score             SMALLINT    CHECK (score BETWEEN 0 AND 100),
    time_ms           INTEGER,
    memory_kb         INTEGER,
    passed_tests      SMALLINT,
    total_tests       SMALLINT,
    compile_log       TEXT,
    security_message  TEXT,
    error_message     TEXT,

    worker_id         VARCHAR(64) REFERENCES workers(id) ON DELETE SET NULL,
    attempts          SMALLINT    NOT NULL DEFAULT 0 CHECK (attempts BETWEEN 0 AND 3),
    attempt_token     UUID,                               -- V11: chặn stale result sau Failover

    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ,

    CONSTRAINT fk_submissions_contest_problem
        FOREIGN KEY (contest_id, problem_id) REFERENCES contest_problems(contest_id, problem_id),
    CONSTRAINT ck_submissions_verdict_when_finished
        CHECK ((status = 'FINISHED') = (verdict IS NOT NULL)),
    CONSTRAINT ck_submissions_finished_at
        CHECK ((status IN ('FINISHED','FAILED')) = (finished_at IS NOT NULL))
);

-- Khôi phục FIFO queue khi Master restart
CREATE INDEX ix_submissions_pending ON submissions(id)
    WHERE status IN ('IN_QUEUE','COMPILING','TESTING');
```

## 2. State machine — `submissions.status`

```
                    POST /api/submissions
                    Master ghi DB + enqueue
                           │
                           ▼
                       ┌─────────┐
                       │ IN_QUEUE│◀─────────────────────────┐
                       └────┬────┘                          │
                            │ Master dispatchNext()          │ attempt++ ≤ 3
                            │ OP_TASK_ASSIGN                 │ (Failover)
                            ▼                               │
                      ┌──────────┐  Worker timeout/disconnect│
                      │COMPILING │───────────────────────────┤
                      └────┬─────┘                          │
               g++ thành   │                                │
               công        │  CE / SEC                      │
                            ├──────────────▶ ┌──────────┐  │
                            ▼                │ FINISHED │  │
                       ┌─────────┐           └──────────┘  │
                       │ TESTING │──────────────────────────┤ Worker timeout
                       └────┬────┘  attempt++ ≤ 3           │
                            │                               │
                  Tất cả    │                               │
                  test xong │                               │
                            ▼                               │
                       ┌──────────┐          ┌────────┐     │
                       │ FINISHED │          │ FAILED │◀────┘ attempt > 3
                       └──────────┘          └────────┘
```

### Bảng transition

| Transition | Trigger | Constraint enforce |
|---|---|---|
| `IN_QUEUE` → `COMPILING` | Master `dispatchNext()` gửi OP_TASK_ASSIGN; Worker nhận | Worker phải IDLE trong activeWorkers map |
| `COMPILING` → `TESTING` | Worker gửi OP_TASK_STATUS {status:"TESTING"} | — |
| `COMPILING` → `FINISHED` (CE/SEC) | Worker gửi OP_TASK_RESULT với verdict CE hoặc SEC | `CHECK (status='FINISHED') = (verdict IS NOT NULL)` |
| `TESTING` → `FINISHED` | Worker gửi OP_TASK_RESULT với verdict đầy đủ | `CHECK (status='FINISHED') = (verdict IS NOT NULL)` |
| `COMPILING/TESTING` → `IN_QUEUE` | `checkHeartbeats()` phát hiện PONG missing > 15s | `CHECK attempts BETWEEN 0 AND 3` |
| `IN_QUEUE` → `FAILED` | `sub.requeue()` khi attempt đã = 3 | `CHECK attempts BETWEEN 0 AND 3` |

> Không có transition nào "ẩn" — mọi thay đổi status đều đi kèm INSERT vào `submission_events`.

## 3. Business rule enforcement

| Rule | Mechanism | SQL |
|------|-----------|-----|
| Chặn nộp ngoài giờ thi | TRIGGER BEFORE INSERT | `trg_submissions_contest` — kiểm tra `created_at BETWEEN start_at AND end_at` và user đã đăng ký |
| Verdict ↔ Finished | CHECK constraint | `CHECK ((status = 'FINISHED') = (verdict IS NOT NULL))` |
| finished_at ↔ terminal state | CHECK constraint | `CHECK ((status IN ('FINISHED','FAILED')) = (finished_at IS NOT NULL))` |
| Max failover | CHECK constraint | `CHECK attempts BETWEEN 0 AND 3` |
| Source code size | CHECK constraint | `CHECK octet_length(source_code) <= 65536` |
| Token security | Schema design | Chỉ lưu SHA-256(token) — lộ DB không dùng lại được |
| Contest problem FK | COMPOSITE FOREIGN KEY | `FK (contest_id, problem_id) → contest_problems` — chỉ nộp bài thuộc kỳ thi |

### Trigger `trg_submissions_contest`

```sql
CREATE FUNCTION check_contest_submission() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE c contests%ROWTYPE;
BEGIN
    IF NEW.contest_id IS NULL THEN RETURN NEW; END IF;
    SELECT * INTO c FROM contests WHERE id = NEW.contest_id;
    -- Chặn nộp ngoài thời gian thi
    IF NEW.created_at < c.start_at OR NEW.created_at >= c.end_at THEN
        RAISE EXCEPTION 'Kỳ thi % không trong thời gian làm bài', NEW.contest_id
            USING ERRCODE = 'check_violation';
    END IF;
    -- Chặn nếu chưa đăng ký
    IF NOT EXISTS (
        SELECT 1 FROM contest_participants p
        WHERE p.contest_id = NEW.contest_id AND p.user_id = NEW.user_id
    ) THEN
        RAISE EXCEPTION 'Người dùng % chưa đăng ký kỳ thi %', NEW.user_id, NEW.contest_id
            USING ERRCODE = 'check_violation';
    END IF;
    RETURN NEW;
END;
$$;
CREATE TRIGGER trg_submissions_contest BEFORE INSERT ON submissions
    FOR EACH ROW EXECUTE FUNCTION check_contest_submission();
```

### V11 migration spec

```sql
-- V11__attempt_token.sql
ALTER TABLE submissions
    ADD COLUMN IF NOT EXISTS attempt_token UUID;

COMMENT ON COLUMN submissions.attempt_token IS
    'UUID được Master tạo mỗi lần giao task (OP_TASK_ASSIGN). '
    'Worker echo lại trong OP_TASK_RESULT. '
    'Master từ chối result nếu token không khớp — chặn stale result sau Failover.';
```

> **Tại sao cần:** Khi Failover xảy ra, Worker cũ có thể hoàn thành chậm và gửi kết quả về sau khi Worker mới đã nhận task. Không có token, Master không phân biệt được result của attempt nào. Với `attempt_token`, mỗi attempt có UUID riêng — result từ attempt cũ bị bỏ qua.

## 5. Views cho API

### `v_problem_stats`

```sql
-- Phục vụ: GET /api/problems
CREATE VIEW v_problem_stats AS
SELECT p.id AS problem_id,
       (SELECT count(*) FROM test_cases t WHERE t.problem_id = p.id) AS test_count,
       count(s.id)                                              AS total_submissions,
       count(s.id) FILTER (WHERE s.verdict = 'AC')              AS accepted_submissions,
       count(DISTINCT s.user_id) FILTER (WHERE s.verdict = 'AC') AS solved_users
FROM problems p
LEFT JOIN submissions s ON s.problem_id = p.id AND s.status = 'FINISHED'
GROUP BY p.id;
```

### `v_leaderboard`

```sql
-- Phục vụ: GET /api/leaderboard
-- RANK: tổng điểm DESC, số bài AC DESC, last AC time ASC
CREATE VIEW v_leaderboard AS
SELECT rank() OVER (
           ORDER BY sum(b.best_score) DESC,
                    count(*) FILTER (WHERE b.solved) DESC,
                    max(b.first_ac_at) ASC NULLS LAST
       ) AS rank,
       u.id, u.username, u.full_name,
       count(*) FILTER (WHERE b.solved) AS solved,
       sum(b.best_score)                AS score,
       sum(b.attempts)                  AS attempts,
       max(b.first_ac_at)               AS last_ac_at
FROM v_user_problem_best b
JOIN users u ON u.id = b.user_id
GROUP BY u.id;
```

### `v_contest_cells` (intermediate cho standings)

```sql
-- Ô ICPC per (contest, user, problem)
-- solved, wrong count, penalty_minutes, first_solve flag
-- Phục vụ: v_contest_standings
CREATE VIEW v_contest_cells AS
WITH subs AS (
    SELECT s.contest_id, s.user_id, s.problem_id, s.status, s.verdict, s.created_at,
           min(s.created_at) FILTER (WHERE s.verdict = 'AC')
               OVER (PARTITION BY s.contest_id, s.user_id, s.problem_id) AS first_ac_at
    FROM submissions s JOIN contests c ON c.id = s.contest_id
    WHERE s.created_at < c.end_at
)
SELECT sb.contest_id, sb.user_id, sb.problem_id, cp.label,
       coalesce(bool_or(sb.verdict = 'AC'), FALSE) AS solved,
       count(*) FILTER (WHERE sb.status = 'FINISHED'
           AND sb.verdict NOT IN ('AC','CE','SEC')
           AND (sb.first_ac_at IS NULL OR sb.created_at < sb.first_ac_at)) AS wrong,
       floor(extract(epoch FROM min(sb.first_ac_at) - c.start_at) / 60)::int AS solve_minute,
       coalesce(min(sb.first_ac_at) = min(min(sb.first_ac_at))
                    OVER (PARTITION BY sb.contest_id, sb.problem_id), FALSE) AS first_solve
FROM subs sb
JOIN contests c ON c.id = sb.contest_id
JOIN contest_problems cp ON cp.contest_id = sb.contest_id AND cp.problem_id = sb.problem_id
GROUP BY sb.contest_id, sb.user_id, sb.problem_id, cp.label, c.start_at;
```

### `v_contest_standings`

```sql
-- Phục vụ: GET /api/contests/:id/standings
-- RANK ICPC: solved DESC, penalty ASC
-- Thí sinh đã đăng ký nhưng chưa nộp vẫn có dòng (0 bài, 0 phút)
CREATE VIEW v_contest_standings AS
WITH totals AS (
    SELECT p.contest_id, p.user_id,
           count(*) FILTER (WHERE cc.solved) AS solved,
           coalesce(sum(cc.solve_minute + cc.wrong * c.penalty_minutes)
                    FILTER (WHERE cc.solved), 0) AS penalty
    FROM contest_participants p
    JOIN contests c ON c.id = p.contest_id
    LEFT JOIN v_contest_cells cc ON cc.contest_id = p.contest_id AND cc.user_id = p.user_id
    GROUP BY p.contest_id, p.user_id
)
SELECT t.contest_id,
       rank() OVER (PARTITION BY t.contest_id ORDER BY t.solved DESC, t.penalty ASC) AS rank,
       t.user_id, u.username, u.full_name, t.solved, t.penalty
FROM totals t JOIN users u ON u.id = t.user_id;
```

## 6. Idempotency design

### Vấn đề

Worker có thể gửi `OP_TASK_RESULT` nhiều lần do network retry, hoặc Worker cũ gửi result sau khi Master đã Failover sang Worker mới.

### Giải pháp hiện tại

```sql
-- finish() trong JudgeMasterService
UPDATE submissions
SET status = 'FINISHED', verdict = ?, score = ?, finished_at = now()
WHERE id = ? AND status IN ('COMPILING', 'TESTING');
-- Nếu submission đã FINISHED: rows affected = 0 → no-op
```

DB CHECK constraint bảo vệ thêm lớp:
```sql
CHECK ((status = 'FINISHED') = (verdict IS NOT NULL))
-- → Không thể ghi verdict=NULL vào row đã FINISHED
```

### Giải pháp đề xuất — `attempt_token`

```
Master                              Worker
  │                                   │
  │ OP_TASK_ASSIGN                     │
  │ {submissionId: 1001,               │
  │  attemptToken: "uuid-v4-A"}        │
  │──────────────────────────────────▶ │
  │                                   │ [chấm bài...]
  │ OP_TASK_RESULT                     │
  │ {submissionId: 1001,               │
  │  attemptToken: "uuid-v4-A",        │
  │  verdict: "AC"}                    │
  │ ◀────────────────────────────────  │
  │                                   │
  │ attemptToken khớp → chấp nhận ✓   │

--- Failover scenario ---

Master                     Worker-1 (chậm)     Worker-2
  │                            │                  │
  │ ASSIGN {token: "A"}        │                  │
  │───────────────────────────▶│                  │
  │                            │ [đang chấm...]   │
  │ timeout → Failover         │                  │
  │ ASSIGN {token: "B"}        │                  │
  │──────────────────────────────────────────────▶│
  │                            │                  │ [đang chấm...]
  │ RESULT {token: "A"}        │                  │
  │◀───────────────────────────│                  │
  │ token "A" ≠ current "B"    │                  │
  │ → BỎ QUA ✗                 │                  │
  │                            │                  │ RESULT {token: "B"}
  │◀──────────────────────────────────────────────│
  │ token "B" = current "B"    │                  │
  │ → CHẤP NHẬN ✓              │                  │
```

> **Novelty cho báo cáo:** `attempt_token` là cơ chế đảm bảo exactly-once result processing trong distributed judge system — tương tự idempotency key trong payment systems, áp dụng vào bài toán online judge.
